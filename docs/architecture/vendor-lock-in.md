# Как снизить зависимость от одного AI-провайдера

> **Тип материала:** архитектурный разбор. **Статус:** концепция и пример проектирования; не отчёт о проверенных нагрузочных тестах.

## Проблема

Когда рабочий процесс целиком завязан на один сервис, лимиты, изменения тарифов, доступности или API становятся проблемой команды. Это **vendor lock-in** — зависимость от поставщика.

## Контекст

Речь о разработке с AI-агентами, где инструмент работы с кодом и модель могут быть разделены. Например, OpenCode может выступать клиентом, а DeepSeek, Z.ai/GLM или Kimi — разными источниками моделей при наличии подходящих API и условий доступа.

## Варианты и компромиссы

| Подход | Преимущества | Недостатки |
| --- | --- | --- |
| Один провайдер и его CLI | Меньше настроек, цельная интеграция | Единая точка отказа, зависимость от тарифов и правил |
| Независимый клиент + несколько API | Переключение моделей, сравнение стоимости и качества | Различия в tool calling, контекстах, кэшировании и поведении |
| Собственный API-шлюз | Единая точка конфигурации и контроля | Дополнительная эксплуатация, задержка, стоимость, новая точка отказа |
| Локальные модели | Контроль над инфраструктурой и данными | Требования к железу, ограничения качества и поддержки инструментов |

## Выбранный подход для стартового эксперимента

Для личного AI-coding workflow разумно начать с **независимого клиента и нескольких совместимых API**, не строя шлюз преждевременно. OpenCode — кандидат, а не универсально лучший выбор.

См. [пошаговую настройку OpenCode](/guides/opencode-setup) и [Claude Code CLI](/guides/claude-code-cli).

## Риски

- **Совместимость:** одинаковый протокол API не означает одинаковые способности модели и поведение агента.
- **Безопасность:** агент получает доступ к проекту, а API-провайдер — к отправленному контексту. Проверяйте политику данных.
- **Стоимость:** сравнивайте полную цену запросов с учётом output, контекста, кэша и повторных попыток.
- **Правила использования:** доступность из сети не равна разрешению пользоваться сервисом из региона.
- **Операционность:** fallback надо проверять на реальных задачах, а не только по успешному ping.

## Как проверить решение

1. Выбрать типовой репозиторий без секретов.
2. Повторить одинаковые задачи на каждой модели.
3. Измерить стоимость, время, корректность diff и работу инструментов.
4. Смоделировать недоступность основного провайдера.
5. Задокументировать версии CLI, ОС, модель и результат.

**Пока не проведены эти проверки, не утверждаем, что система отказоустойчива.** Несколько настроенных провайдеров не обеспечивают автоматический failover.

## Вывод

Независимость — не число подключённых моделей, а возможность **контролируемо переключиться** без потери безопасности и предсказуемости. А если хочется пошутить: в архитектуре это называется снижением vendor lock-in, в личной жизни — открытыми отношениями.
